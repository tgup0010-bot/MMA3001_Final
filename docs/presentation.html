The Problem

Office buildings have CO2 sensors, but most systems only react after the air has already gone bad. By the time the ventilation kicks in, occupants have been sitting in stale air.

What we want to do

  • Predict CO2 level 15 minutes ahead
  • Use the recent sensor history + building occupancy
  • Give the building management system early warning so ventilation can ramp up before the problem arrives

Why this matters

  • CO2 above ~800–1000 ppm affects alertness and comfort
  • Proactive ventilation = better air quality + less energy waste
  • A 15-minute forecast is actionable — a building system can actually respond in time
Regression task: predict a continuous CO2 value (ppm) — not a category
→ Compared all four Week 5 regression methods on real sensor data

Methods — Four Regression Models (Week 5)

All four Week 5 regression methods were implemented and compared — not just one chosen by preference. Each runs through the same StandardScaler preprocessing step for a fair comparison.

Linear Regression

Fits a straight-line relationship. Simplest and most interpretable — useful as a baseline to beat.

Decision Tree Regression

Splits data into if/else regions (max depth 8). Can capture combinations like "high CO2 + busy afternoon" that a linear model misses.

SVR (RBF kernel)

Fits a smooth nonlinear curve, tolerant of small errors. C=10, ε=0.5. Works well on mid-sized datasets with mild nonlinearity.

Neural Network

Two hidden layers (32 + 16 units), early stopping. Most flexible but also most prone to overfitting on a dataset this size.

💡

Occupancy was included as a testable feature, not assumed useful. Section 4 tests it directly — with and without — because the sensor has no documented room, so it was not obvious that occupancy would be relevant.

Key Finding — Does Occupancy Help?

Each model was run twice — once with building occupancy as a feature, once without. The results are clear:

ModelR² with occupancyR² without occupancyVerdict

Decision Tree0.19140.3305Gets worse

Neural Network0.33600.3352No difference
⚠️

Occupancy does not improve CO2 prediction for any model. For Decision Tree, it actively hurts — the model wastes splits on an irrelevant feature.

🔍

Why? Sensor 6012002000326 has no documented room location. A prior correlation check across all 5 zones found max |r| ≤ 0.06 for CO2. The sensor likely measures a shared corridor or building-wide airflow — not a specific occupancy zone. This is a finding, not a flaw — it was tested and reported honestly.

Missing Data — What Was Found and How It Was Handled

The gap problem

  • 636-day sensor outage in the data
  • Readings are not evenly spaced
  • 84,576 raw candidate rows → only 17,010 usable (20%)
  • Rest dropped — filling a 636-day gap with made-up values would be far worse

How it was handled

  • Rows missing any lag/rolling/target value → dropped
  • Integration step needed a gap-aware fix (see next slide)
  • Both issues reported explicitly rather than hidden
📋

Other data quality issues found along the way: Two sensors had frozen clocks (discovered by profiling). The occupancy log file named "MayToDec2024" actually covers November 2023 to April 2026 — only found by checking the actual timestamps. The dataset description documents none of this.

Numerical Integration — Week 6 Application

CO2 exposure over time = area under the CO2-vs-time curve. Trapezoidal rule and Simpson's 1/3 rule implemented from Week 6 formulas (not a library).

🐛

Bug caught: First version resampled onto a 15-min grid and dropped gaps — this made the 636-day outage look like a single 15-min step. Simpson's rule gave ~1.1M ppm·h vs trapezoidal ~9.5M ppm·h. A 9× difference between methods that should broadly agree = clear signal something was wrong.

✅

Fix: Gap-aware trapezoidal — skips any panel spanning more than 2 hours. Gap-aware: 2,305,836 ppm·h vs naive: 9,543,357 ppm·h (4× difference from bridging assumption alone).

Convergence check on a clean 41-hour window (1–3 Oct 2025):

Limitations and What We'd Do Differently

Sensor has no room location

Not in the official Sensor ID spreadsheet at all. Can't know which occupancy zone to pair it with — this limits what occupancy data can tell us.

R² ≈ 0.34 — moderate result

The model captures about a third of the variance. What's missing: HVAC switching, windows, doors, equipment. Useful as a trend signal, not a precise forecast.

What this can't tell us

Whether occupancy would help for a sensor that is co-located with an occupancy counter. That's a different setup — this dataset can't answer it.

What worked well

External validation against BoM data gave confidence in the sensor. Chronological split was correct. All bugs were caught by running code on real data, not by the code looking clean.

💡

If sensor room location were documented: could select the matching occupancy zone, potentially improving prediction. CO2 may also respond better to zone-level occupancy data rather than a building-wide count.

Summary

What was done

  • Predicted indoor CO2 level 15 min ahead — 4 regression models compared
  • SVR performed best: MAE = 8.35 ppm, R² = 0.34
  • Occupancy tested as a feature — found not to help for any model
  • Week 6 numerical integration applied to calculate CO2 exposure
  • Real bugs found and fixed throughout

Key takeaways

  • CO2 is driven mainly by ventilation, not individual room headcounts
  • Data quality issues (frozen clocks, undocumented sensor) are common in real industrial datasets
  • A moderate R² reported honestly is valid engineering work
  • Convergence checks caught a real integration bug that code review alone would have missed
Best model: SVR — 8.35 ppm average error on unseen future data
